# LLM 분류기를 정적 파서 뒤에 둔다

`command not on read-only allowlist`는 거부 로그에서 가장 큰 버킷이고, 그 안의 값은 `docker`, `kubectl`, `npm`처럼 서브커맨드 지식이 있어야 판정할 수 있는 명령들이다. 각각에 체커를 쓰는 것은 끝이 없으므로, 정적 파서가 거부한 명령 중 **명령어를 몰라서** 거부한 것만 LLM에 재심을 맡기고 판정이 읽기 전용이면 자동 승인한다. 정적 파서는 그대로 앞에 남아 아는 것을 ~14 ms에 처리하고, LLM은 지금 사람에게 프롬프트가 뜨는 자리에만 붙는다.

## Considered Options

README의 "왜 auto 모드로 해결하지 않는가" 절이 LLM 판정을 쓰지 않는 이유를 논증하므로, 이 결정은 그 절을 부분적으로 뒤집는다. 뒤집는 근거는 auto 모드가 실제로는 계층형이라는 것이다 — Claude Code 2.1.220을 뜯어보면 분류기 앞에 공짜 관문 둘(도구 안전 목록, `acceptEdits` 재검사)이 있고 거기 걸리면 LLM을 부르지 않는다. 여기서는 정적 파서가 그 자리를 맡는다.

대안 넷을 각각의 이유로 버렸다.

- **`prompt` 훅 / `agent` 훅.** Claude Code가 세션 인증으로 LLM을 직접 돌려주므로 서브프로세스가 없다. 그러나 출력 계약이 `{ok, reason}` 하나뿐이라 **거부만 가능하고 승인을 못 낸다**. `ok:true`는 권한 결정을 내지 않아 평소 프롬프트가 그대로 뜬다.
- **극성 반전** — 정적 허용을 넓히고 `prompt` 훅에 거부권을 준다. auto 모드의 실제 모양이지만, 훅이 오류를 내면 `outcome:"non_blocking_error"`로 지나가므로 관대한 기반이 그대로 남아 fail open이 된다. 이 프로젝트의 편향은 default deny다.
- **`http` 훅 + 상주 헬퍼.** 승인을 낼 수 있고 기동 비용도 없지만, 설치자가 데몬을 띄우고 살려둬야 한다. 훅 하나를 배포하는 프로젝트에 무겁다.
- **정적 파서 대체.** `ls` 하나에도 네트워크 왕복이 든다.

`claude -p`를 고른 것도 배포 조건 때문이다. 이 훅을 설치하는 사람은 정의상 Claude Code 사용자이므로 바이너리와 인증을 이미 가졌다. API 키는 아니고, 로컬 모델도 아니다.

## Consequences

- 판정에 **3~4초**가 든다(측정: 3.18 / 3.92 / 4.41 s). 그 자리는 원래 사람이 프롬프트를 보고 누르던 자리다.
- LLM이 허용하면 그 명령어를 이번 줄에 한해 허용 목록에 넣고 **파서를 다시 돌린다.** 통과할 때만 승인이 나간다. LLM의 권한이 "명령어 이름 하나를 추가한다"로 묶이고, 리다이렉션·백틱·`cd` 다음 `git` 같은 구조적 규칙은 LLM 판정과 무관하게 산다.
- 구조적 거부와 파괴적 명령 하드 목록은 **LLM을 부르지도 않는다.** 오판의 폭발 반경이 미지 명령어로 제한된다.
- 기본값은 off다. `PLAN_MODE_AUTOALLOW_LLM=on`으로만 켜진다. 갱신만 한 사람이 모르는 사이 토큰을 쓰지 않는다.
- 허용 판정은 적립되어 캐시이자 정적 규칙 승격 후보가 된다. 오판 하나가 영속하는 대가를 지지만, 같은 줄이 오늘과 내일 다르게 판정되지 않는다.
